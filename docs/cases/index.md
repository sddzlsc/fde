## 怎么读案例：六格画布

市面上讲 FDE 的文章，常把案例写成传奇：某公司派工程师进驻，几个月后客户起死回生。这种写法无法复用，因为缺了最关键的信息——条件、口径和代价。

本书统一用六格画布拆案例。读任何一个案例，先把它填满，再谈能不能学：

| 画布 | 要问的问题 | 危险信号 |
| --- | --- | --- |
| 背景 | 客户是谁、什么行业、什么规模、什么时间 | 只有公司名，没有客户与场景 |
| 问题 | 哪个具体流程、基线是多少、谁最痛 | 从「我们用了大模型」讲起 |
| 做法 | 谁进现场、做了哪几步、花了多久 | 只写技术栈，不写人与流程 |
| 指标 | 业务结果是什么、口径是什么、和什么比 | 只有提升幅度，没有基线 |
| 可迁移经验 | 哪条机制换一家客户仍然成立 | 依赖特殊关系或独家数据 |
| 口径与限制 | 谁披露的、是否独立、样本多大 | 全篇「据报道」，无一处可追 |

填充时有一个简单原则：**先看口径，再看数字**。同一句「效率提升 70%」，可能是单环节耗时、可能是客户自报、也可能是第三方审计，三者的证据强度完全不同。

## 可信度分级：别让「据称」混进结论

本书沿用统一标签。正文中出现数字时，都会带其中一个：

| 分级 | 含义 | 怎么用 |
| --- | --- | --- |
| **A 公司披露 / 官方** | 财报、官方博客、官方客户案例、政府或学校官网 | 可作事实引用，但要记住厂商有立场 |
| **B 多源** | 两个以上独立来源交叉 | 可作事实引用，仍需看各自口径 |
| **C 单源** | 只有一家媒体、播客、自述或二手转述 | 写「据……报道（单一来源）」，不作唯一依据 |
| **D 估算 / 综合** | 第三方估算、多来源综合、作者归纳 | 写「第三方估算 / 综合」，不当官方数字 |
| **待核** | 付费墙、原始链接被拦截、细节存疑 | 正文尽量不用；必须用时明确标「待核」 |

::: warning 三种最常见的口径错误
把「第三方估算」写成「官方定价」；把「客户自报」写成「独立验证」；把「增长率」写成「岗位数量」。本书在案例页逐条标注，读的时候请一起看。
:::

## 案例是证据，不是模板

把这份索引当模板库用，是最常见的误用。至少有三层原因：

1. **幸存者偏差**：被写出来的几乎都是成功案例，失败的项目没人写新闻稿。你看到的是分子，不是分母。
2. **特殊条件不可见**：标杆客户往往有高层支持、数据开放、预算充足等条件；这些在案例里通常被省略。
3. **口径不一致**：同一个「解决率」，各家公司定义不同；直接横向比较会得出错误结论。

正确用法是把它当**假设来源**：看到别人的做法，先问「它在什么条件下成立」，再用你自己的现场五问去验证——谁痛？痛多大？现在怎么解？为什么是现在？谁为结果买单？

## 读案例的三个反模式

- **抄打法，不抄条件。** 只记住「派工程师驻场」，忘了对方有高管 sponsor 和干净数据。
- **只看数字，不看口径。** 把供应商案例里的「提升 70%」直接写进自己的项目章程。
- **用案例下行业结论。** 三家公司的做法不等于行业规律；样本量根本不够。

## 本章小结与给读者的启示

- 读案例先填六格画布：背景、问题、做法、指标、可迁移经验、口径与限制。
- 可信度分级不是装饰：A 也带厂商立场，C 也能提供线索，D 必须写成估算。
- 68 个条目覆盖四条线：Palantir 的原点、AI 原生公司的增长引擎、大企业的现场、中国的约束条件。
- 把案例当假设来源，而不是模板；你的现场条件，才是决定动作的那一半。
