# 实战 Lab · 三个可独立完成的项目

<div class="chapter-meta">
  <span><strong>预计投入</strong> 12-20 小时 / 个</span>
  <span><strong>难度</strong> ★★☆ - ★★★</span>
  <span><strong>前置</strong> 第 6、7 章</span>
  <span><strong>数据</strong> 合成 / 公开</span>
</div>

> 本章你会学到：三个 Lab 该怎么选、环境怎么搭、作品集按什么标准验收，以及怎么判断自己是真的做完了，而不是「跟着教程跑通了」。
>
> 一句话：Lab 不是教程，是三份迷你交付合同；验收标准是「别人能复现、能判断好坏」，不是「代码能跑」。

## 一个现场片段

> 以下为合成场景，用于说明典型情境，不对应任何真实项目。

你读完了前六章，概念都懂：现场五问、六阶段、价值证据金字塔。然后你打开一个真实需求——客服工单分错、合同看不完、内部知识找不到——突然发现无从下手：数据在哪？标签怎么定？什么叫「做得好」？

这个卡点是正常的。**从「知道方法」到「交付结果」之间，隔着一个完整项目的肌肉记忆**。三个 Lab 就是为这段过渡设计的：每个都足够小，能在十几小时内做完；又足够完整，能让你走一遍发现、定义、原型、评测、上线检查和复盘。

## Labs 是什么，不是什么

- **是**：一个可复现的小项目、一份评测报告、一份上线检查清单、一次复盘。做完你会拥有一页能放进作品集的材料。
- **不是**：跟着视频敲一遍的教程。代码只是载体，**真正的产出是「你怎么定义问题、怎么证明有效、怎么控制风险」**。

每个 Lab 有三种用法，按你的时间选：

| 用法 | 做什么 | 适合谁 | 耗时 |
| --- | --- | --- | --- |
| 跟读 | 用页面里的合成数据和方法跑通流程 | 第一次做项目 | 8-12 小时 |
| 独立 | 只看章节结构，自己造数据、自己设计评测 | 有开发经验 | 12-16 小时 |
| 改造 | 把场景换成你熟悉的业务（如招聘筛选、售后 FAQ） | 想直接用于工作 | 16-24 小时 |

::: tip 只做一个，但要做完
同时开三个 Lab 是最常见的死法。选一个做完、写成作品集，比三个都停在「跑通 demo」有价值得多。
:::

## 怎么选

| Lab | 场景 | 适合谁 | 技术重点 | 产出 | 难度 | 时间 |
| --- | --- | --- | --- | --- | --- | --- |
| [A · 客服工单智能分流](/labs/lab-a-ticket-triage) | 工单分类与分派 | 想练完整六阶段的人 | 分类 + 置信度 + 人工复核 | 分流系统 + 评测报告 | ★★☆ | 15-20 小时 |
| [B · 合同条款审查](/labs/lab-b-contract-review) | 合同风险条款识别 | 法务、采购、咨询背景 | RAG + 引用校验 + 缺失检查 | 审查助手 + 漏检分析 | ★★★ | 12-16 小时 |
| [C · 企业知识助手](/labs/lab-c-knowledge-copilot) | 内部知识问答 | 企业 IT、产品、知识管理 | 检索 + 权限 + 无答案处理 | 知识助手 + 权限红队 | ★★★ | 12-16 小时 |

怎么选，看三个问题：

- 想先建立完整项目感、以后再做文档类场景 → **选 A**，它的六阶段最完整；
- 对合规、法务、合同、风险敏感，或想练「引用与核对」→ **选 B**；
- 在企业内部做落地、关心权限与知识治理 → **选 C**。

三个都做也可以，建议顺序 A → B → C：A 练闭环，B 练引用与缺失检查，C 练权限与拒答。

## 环境准备

### 你需要什么

| 组件 | 最低要求 | 说明 |
| --- | --- | --- |
| Python | 3.11+ | Lab 代码以 Python 为例；也可用 Node 20+ 实现 |
| Node.js | 20+（可选） | 只在你想用 TypeScript 或做演示页时需要 |
| 编辑器 | VS Code / Cursor 等 | 能调试、能看 JSON |
| Git | 任意版本 | 版本管理，也是作品集的一部分 |
| LLM 访问 | 三选一，见下表 | 没有 API key 也能做 |
| 向量库 | 可选 | 小数据量用内存 / SQLite 就够，不必上 Milvus |
| GPU | 不需要 | 本地跑小模型是加分项，不是门槛 |

### LLM 访问的三种模式

| 模式 | 怎么用 | 成本 | 适合 |
| --- | --- | --- | --- |
| 云端 API（OpenAI 兼容） | 用 `OPENAI_BASE_URL` + `OPENAI_API_KEY` 调任意兼容网关 | 约 5-20 美元可完成一个 Lab | 想验证真实效果 |
| 本地模型 | Ollama / llama.cpp 等，按硬件选小模型 | 电费 + 硬件 | 数据不能出本机、想离线 |
| 纯离线模拟 | 写一个 stub 返回固定 JSON，或只用规则基线 | 0 | 先跑通流程、写评测脚本 |

**API key 是可选的，但「真实调用一次」建议保留**：模拟能验证流程，不能验证模型行为。

```bash
# 建议用 .env 管理，不要把 key 写进代码或提交到仓库
export OPENAI_API_KEY="你的 key"
export OPENAI_BASE_URL="你的兼容网关地址，可选"
export LLM_MODEL="你使用的模型名"
```

```bash
# Python 环境
python3 -m venv .venv
source .venv/bin/activate
pip install openai pandas scikit-learn
```

::: danger 三条数据红线
1. 只用合成数据、公开数据或已获书面授权的脱敏数据；**不要用真实客户数据、员工数据、合同**。
2. 不要把敏感内容提交到仓库、截图、演示视频或第三方 API。
3. 公开数据要确认许可证允许学习用途，并在 README 里写清来源。
:::

### 建议的项目结构

```text
lab-a/
  README.md          # 问题、指标、如何运行
  data/              # 合成数据 + 生成脚本（固定随机种子）
  src/               # 分类/检索/生成代码
  eval/              # 评测集与评测脚本
  reports/           # 评测报告、截图
  .env.example       # 环境变量示例（不含真实 key）
```

三条工程约定，直接决定作品集质量：

1. **数据可重建**：提供生成脚本和随机种子，别人能生成同一份数据；
2. **评测可一键跑**：一条命令输出全部指标；
3. **报告可读**：不打开代码也能看懂结论、口径和局限。

## 作品集标准

做完一个 Lab，按下面六项验收。每一项都给「通过 / 不通过」的判断依据。

| 标准 | 通过的样子 | 不通过的样子 |
| --- | --- | --- |
| 问题与基线 | 一段话说清谁痛、现在怎么解、基线是多少 | 只有「我做了个 AI 工具」 |
| 方案与取舍 | 架构图 + 为什么这样选（含放弃的方案） | 罗列技术栈，没有取舍 |
| 评测报告 | 评测集结构、主指标、分层结果、错误分析齐全 | 只有一张截图或一个准确率 |
| 成本与延迟 | 单次成本、P95、规模估算都算过 | 「大概不贵」 |
| 上线与安全 | 检查清单、灰度、回滚、人工复核有具体动作 | 只有「已测试」 |
| 复盘 | 写清失败、误判和改进 | 只写成绩，全是夸奖 |

加分项：有真实用户试用反馈、有 5 分钟演示视频、仓库能被别人复现、被社区指出问题并改进。

::: warning 常见夸大，别写
「准确率 95%」却不说是哪个集合、多少样本；「效率提升 10 倍」却没算人工时间；Demo 很酷但没有评测。**面试官最容易追问的就是口径**，夸大一次就会失去信任。
:::

## 交付清单（所有 Lab 通用）

<ul class="checklist">
  <li>README：问题、用户、指标口径、如何运行</li>
  <li>数据说明：来源、合成方法、许可证、集合划分</li>
  <li>可运行代码：一条命令跑通主流程与评测</li>
  <li>评测报告：总表、分层结果、错误分析、局限</li>
  <li>架构图或数据流图（ASCII 也可）</li>
  <li>上线检查清单与回滚方案</li>
  <li>5 分钟演示脚本（含「哪里会失败」）</li>
  <li>复盘：做对了什么、失败在哪、重做会怎么改</li>
</ul>

## 6 周节奏建议

每周 8-10 小时，适合在职学习：

| 周 | 做什么 | 本周产出 |
| --- | --- | --- |
| 第 1 周 | 选 Lab、搭环境、写项目章程、造数据 | 一页章程 + 数据说明 |
| 第 2 周 | 规则基线 + 评测集 v1 | 基线结果 |
| 第 3 周 | 模型 / 检索方案 + 提示词迭代 | 可演示原型的 v1 |
| 第 4 周 | 评测、错误分析、指标对比 | 评测报告 v1 |
| 第 5 周 | 上线检查、灰度方案、安全清单 | 上线就绪包 |
| 第 6 周 | 作品集包装、演示、复盘 | 作品集一页纸 + 复盘 |

## 怎么判断自己真的做完了

找一个人（同学、同事、社区里的陌生人），让他只看你的 README 和报告，回答三个问题：

1. 你能复现这个结果吗？
2. 指标是在什么数据、什么口径下得到的？
3. 系统出错时会发生什么，怎么退回来？

三个都能答上来，才算做完。答不上来，回去补文档或补评测——这本身就是 FDE 工作的一部分。

## 常见误区

- **同时开三个 Lab**：精力分散，最后三个都是半成品。
- **只跑 demo 不写评测**：demo 是演示，评测才是证据。
- **追求花哨技术栈**：向量库、Agent 框架堆一堆，却说不清基线是多少。
- **忽视数据许可**：拿真实数据做实验，作品集变事故。
- **把「跟教程跑通」当作品**：没有自己的取舍和失败记录，面试里讲不出深度。

## 本章小结

- 三个 Lab 是三份迷你交付合同，验收标准是「可复现、可判断好坏」。
- 按背景选一个做完，比三个都浅尝更有价值；推荐顺序 A → B → C。
- 环境门槛不高：Python + 可选 API key，没有 key 也能用模拟模式跑通。
- 作品集看六项：问题与基线、方案取舍、评测、成本延迟、上线安全、复盘。
- 数据和合规是红线，合成与公开数据足够完成全部 Lab。

## 练习

1. **选一个 Lab，写一页项目章程**：问题、用户、指标、边界、数据来源、风险。判断标准：另一个人读完能说出「做什么、不做什么、怎么算成功」。
2. **搭环境并跑通一次调用**：完成 venv、依赖、环境变量，用 OpenAI 兼容接口返回一个 JSON。判断标准：换一台机器能按 README 复现。
3. **用作品集标准自评**：找一份你过去的项目，按六项标准打分。判断标准：至少找出两项「不通过」并写出改进动作。
